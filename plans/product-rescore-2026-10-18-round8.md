# logGraph 产品复评 · 第八轮（2026-10-18）

> 视角：资深产品经理 / 从用户价值出发。
> 前置：第七轮加载模式透明化后 **9.2**（见 `product-rescore-2026-10-18-round7.md`）。
> 本轮做两件事：**删除最后一个 TS 双实现副本**（六/七轮清单里的 ⚠ 项），
> 并借这次删除把 CEP 的失败模式从「静默空结果」改成「显式横幅 + 重试」。

---

## 0. 一句话结论

**`src/sequence/SequenceMatcher.ts`（614 行）删了。CEP 双实现从"冻结副本"变成"零副本"。**

但比删文件更重要的是删除时发现的问题：TS 副本一直充当着**静默兜底**——
wasm 没就绪时悄悄用 TS 跑，而如果连 TS 也跑不了（或将来没有 TS），
用户看到的就是「CEP 面板什么都没有」。没有错误、没有原因、没有重试。
这和第七轮修掉的"加载模式无法归因"是同一类病：**产品状态对用户不可见**。

所以本轮的表面是删除，实质是失败显式化：

- `runCepWasm` 返回显式 outcome（`loading` / `failed` / `unsupported` / `ok`），
  不再有"返回 null = 静默回退"；
- wasm 加载窗口期：重算**延后**到就绪自动执行，保留旧结果不闪空
  （App 启动即预热，窗口与日志解析重叠，正常情况下用户根本感知不到）；
- 引擎真失败：CEP 面板渲染「引擎不可用」横幅（`--danger` UI 报错色）+
  原因 + **重试**按钮；同时抑制「为何没匹配」诊断——零链是"没跑"，
  不是"跑过没匹配上"，此时的诊断全是误诊。

综合 **9.2 → 9.3**。UX **9.1 → 9.2**：又一类"无法归因"被消灭，
且这次连带消灭了一个** correctness 隐患**（把引擎失败伪装成"没有匹配"）。

## 2. 本轮兑现了什么（代码证据）

### ✅ 删除 `SequenceMatcher.ts`（-614 行）
- 全仓零引用后 `git rm`；CEP 语义单一事实来源仅剩 `engine/src/cep.rs`，
  native（Tauri IPC）与 wasm（`cep-wasm`，`#[path]` 共享源）同源编译。

### ✅ `cepWasm.ts`：显式 outcome 契约
```ts
export type CepWasmOutcome =
  | { kind: 'loading' }      // 首次加载窗口期 → 调用方延后重算
  | { kind: 'failed'; error: unknown }   // 加载/运行失败 → 显式报错
  | { kind: 'unsupported' }  // 引擎门控回退（is_supported 恒 true 后不应出现）
  | { kind: 'ok'; results: Record<string, SequenceMatchResult> };
```
- 新增 `onCepWasmSettled(cb)`：加载**落定**（成功或失败都触发）一次性回调。
  失败也唤醒等待者——否则"加载中"会挂成永久状态；
- 新增 `retryCepWasm()`：重置加载状态供 UI 重试。

### ✅ `logStore.recomputeSequences`：单一引擎 + 延后 + 显式错误
- Web 端 wasm 是唯一引擎；dbMode 常规组下推 native，「全排除」跨行组走 wasm；
  **native 异常/回退时以同源 wasm 兜底**（同一份 cep.rs，不是语义分歧的 TS）；
- wasm 在加载 → `cepEnginePending=true` + 注册落定重算，**保留旧结果**；
- 失败 → `cepEngineError` + 清空结果（不拿旧结果冒充新数据）；
- 删除 `seqTsSafeGroups` / `TS_SEQ_EVENT_LIMIT`（TS 引擎 300k 主线程护栏；
  wasm 是原生速度，该护栏失去存在理由）。

### ✅ App 启动预热
- `App.tsx` 与 `ensureRegexWasm` 同款位置加 `ensureCepWasm()`：
  wasm 加载与日志解析重叠，CEP 需要时基本已就绪。

### ✅ `CepTimelinePanel`：横幅 + 重试 + 诊断门控
- 引擎不可用 → 面板**保活**（原逻辑 blocks 空即 `return null`，用户看到"什么都没有"），
  渲染横幅：`CEP 引擎不可用，序列匹配未执行` + 具体原因 + 「重试」；
- 块头计数在引擎挂时显示**配置的组数**（而非 0），避免"0 组规则"的误导；
- `explainNoMatch` 诊断在引擎非 ok 时**抑制**——零链是"没跑"，
  此时的"为何没匹配"全是误诊；
- 加载中 → 中性「CEP 引擎加载中…」提示，不抢注意力。

### ✅ 测试移植（不是删除）
- `threadHint.test.ts` 4 个引擎用例改**直跑 wasm**（vitest node 环境 +
  `readFileSync` + `init({module_or_path})`，与 `scripts/test-wasm-cep.mjs`
  同款加载方式）——覆盖率不降反升：以前测 TS 副本，现在测**真引擎**；
- `npm test` 90/90、`test-wasm-cep.mjs` 10/10、`tsc` 0 错、build 通过。

### ✅ 浏览器双冒烟（本机 chromium + playwright-core）
- **错误态**：注入 `cepEngineError` → 横幅 + 重试按钮渲染、面板存活；
  清掉错误 → 横幅消失（无误报）；
- **正向 E2E**：`setState(filters/groups)` → `recomputeMatches` →
  `recomputeSequences` → wasm → 面板渲染出「1 链」与两步链行
  （ERROR→TIMEOUT），threadStats 正确——证明重构后正常路径没坏。

### ✅ 文档三处同步（记忆里的契约纪律）
- `plans/engine-cli-api-contract.md`：新增 **§3.16**（CEP 单一事实来源收口）、
  重写浏览器模式描述、架构图 `filter-wasm + cep-wasm`；
- `AGENT.md`：删掉"CEP 对齐 SequenceMatcher.ts，改任一侧必须同步另一侧"
  （这条指令现在会把人引向一个不存在的文件）；
- `README.md`：文件树更新。

## 3. 为什么这是 UX 分而不是纯工程分

工程侧的事实是"删了 614 行死代码"；UX 侧的事实是：

1. **消灭了一类静默失败**。引擎跑不了时，旧行为是"面板什么都没有"——
   用户无法区分"没有匹配"和"引擎没跑"。新行为：红色横幅 + 原因 + 重试。
   这与第七轮的加载模式徽标是同一个产品哲学：
   **产品的每个状态都对用户可解释**。
2. **顺带修了一个 correctness 隐患**：引擎失败时旧代码会拿空结果去跑
   「为何没匹配」诊断，给出"过滤器零命中/顺序颠倒"等**完全错误**的归因。
   诊断门控后，误诊不会发生。
3. **加载窗口从"闪空 + 静默 TS"变成"延后 + 旧结果保持"**，首屏不再跳变。
