# logGraph 产品成色评审（2026-10-16）

> 视角：资深产品经理 / 从用户价值出发。
> 依据：README、AGENT.md、`plans/` 设计文档、实际源码与提交记录（dev 分支，最近 25 个 commit）。
> 性质：评估与建议，不含实施排期。

---

## 0. 一句话结论

**方向选对了，引擎打好了，但产品还停在「自用神器」阶段——它缺的不是性能，是闭环和分发。**

内核 8.5 分，外壳 6.5 分。近 10 个 commit 几乎全在补渲染性能与 UI 细节，而
**性能已经过剩**（最坏 4.9s 场景仍有 20× 优化余量），**真正有壁垒的 CEP 只兑现了约 40%**。
这是当前最大的资源配置错配。

## 2. 产品价值：三层用户，三层兑现度

### 第一层 · 排障的开发 / 运维（核心价值，已兑现）

场景：线上「下单偶发超时」，手上有 nginx / app / db 三份日志。
传统做法：三个终端各 grep 一遍，肉眼比对时间戳。
logGraph：三条过滤器三条 lane，一眼看到「app 报 timeout 的时刻，db lane 上 200ms 前有一条 slow query」。

- **价值强度：高，且是差异化价值**（Notepad++ / less / VSCode / Kibana 的 grep 都给不了）
- **兑现度：~85%**

### 第二层 · 把排障经验沉淀成规则的人（最高天花板，半成品）

场景：第三次排查同一类故障，决定写成规则「启动完成后 5s 内必须出现心跳，否则异常」。
CEP 把「人肉模式识别」变成「可复用、可自动执行的资产」。

- **价值强度：最高**（这才是长期壁垒）
- **兑现度：~40%** —— UI 能配，引擎跑不了同样规则；规则也导不出、进不了 CI

### 第三层 · 需要把结论交付给别人的人（未兑现）

场景：找到根因，要写故障报告 / 发群 / 贴工单。
当前：截图、手抄行号、手动复制几段原文。

- **价值强度：中高**
- **兑现度：~10%** —— 无导出、无分享、无行级标注（仅有时间范围书签）

### 价值主张的诚实评价

产品现在卖的是「看得见的关联」，但真正的壁垒在第二层「规则资产化」。
资源明显压在第一层的渲染与性能上。**性能过剩 + 壁垒未建** = 当前最大的战略错配。

## 3. 待改进点（按用户痛感排序，不是按技术债）

### P0 · 不解决就长不大

**① GUI ⇄ 引擎能力不对等，CEP 无法进自动化**
UI 的 `SequenceMatcher.ts` 支持 thread 分桶、循环计数 `A{3}`、条件表达式；
但契约 `engine-cli-api-contract.md` 里 `scope:"thread"` = **W01**、`nodeCounts` = **W04**、
`nodeConditions` = **W05**——引擎 v1 **不计算，直接 fallback**。
后果：用户在画布上精心配好的规则，导出 .cep.json 跑 CLI / CI 时**静默失效**（只有 `fallback=true`）。
这砍掉了 CEP 一半价值：它只能当交互式查看器，不能当无人值守的故障检测。
另外，UI 侧多一份 TS 实现本身也违反 AGENT.md §1「单一实现原则」。
**建议**：三个能力下沉进 engine，契约升 v1.3，删掉 UI 侧重复实现。

**② 规则资产出不了工作区、进不了团队**
规则只存在 `<目录>/.logGraph/filters.json`，与日志目录绑死。
但真实情况：日志在服务器上、只读、或临时拉下来；规则应该跟代码仓库走。
CLI 侧已有完整 `.cep.json` + JSON Schema + `validate` / `schema` 子命令，
**GUI 侧没有导入 / 导出规则文件的入口**。
**建议**：GUI 加「导出为 .cep.json / 导入 .cep.json」。做完这一步，logGraph 才可能
从「个人工具」变成「团队基础设施」。

**③ 分析结果出不去（最后一公里）**
能看到关联，但结论留在工具里。缺：行级标注 / 评论、选中链上下文批量复制、
时间范围书签导出、报告或分享快照。
**建议**：先做最小闭环——「复制选中链的完整上下文（含文件 / 行号 / 时间）为 Markdown」，
成本极低，用户拿到就能贴工单。再补标注与分享快照。

**④ 概览缩放下时间线是两个实心色块（真机实测新增，见附 A ①）**
全量视图（窗宽 206.8h）下 26.8 万命中压缩成 100% 饱和的实心条，
看不到任何结构，**"垂直对齐看关联"这一核心价值在默认缩放下直接失效**。
**建议**：概览层引入密度直方图 / 热力聚合（按时间桶聚合命中数），
缩放到一定粒度再切换为离散事件；或加载后自动缩放到首个有意义的区间。

### P1 · 影响信任与留存

**④ 加载模式对用户不透明（对应 review §1.5）**
同一目录：全选加载 → dbMode（骨架 + rg + 惰性）；拖拽文件夹 / 子集加载 → 全量内存。
**同一份数据、两种能力边界、两种引擎**。用户不知道自己在哪个模式，遇到行为差异无法归因。
**建议**：桌面端统一走 dbMode；或在 UI 明确标注当前模式与能力边界。

**⑤ 性能故事依赖「最佳条件」，最坏情况无反馈**
README 主打 0.21s / 1.73s，但那是 **3.3% 命中率**。
高命中率场景（52%，例如宽泛正则）冷扫描 **4.9s**（`perf-optimization-design.md` 已归因），
且没有进度条。用户写一个 `\bERROR\b` 在错误密集日志里就会撞上。
**建议**：先吃掉已实锤的两块——大小写变体预展开（~1.5s）、输出零 clone（store+join 大头）；
同时扫描期间给**确定性进度 + 可取消**，而不是只有「计算中」。
用户的忍耐阈值不是 5 秒，是「不知道还要多久」。

**⑥ CEP 门槛没被削平——最高价值的功能最容易被放弃**
六种边类型 + 循环计数 + 条件表达式 + thread 作用域，画布打开是空白；
没有模板、没有引导式创建、没有「为什么这条链没匹配上」的解释器。
新用户大概率看一眼就走。
**建议**：① 内置规则模板库（超时未响应 / 重试后失败 / 心跳丢失 / 启动后崩溃 / 死锁征兆）；
② 引导式创建（选模板 → 填参数 → 生成画布）；③ 规则试跑与解释（「第 3 步未匹配：候选 12 条，均因 maxGap 超出」）。

**⑦ 无 CI、无前端测试、无 LICENSE、无 release**
15.6k 行 TS + 6k 行 Rust，**前端零测试**。任何人改 `LogStreamView.tsx`（1648 行）都只能靠手点。
README 声明 MIT 但仓库里**没有 LICENSE 文件**；没有 release 产物、没有更新通道。
**建议**：CI 跑 `cargo test --workspace` + `tsc -b` + `npm run test:wasm`；
前端补 `SequenceMatcher` / `expr` / 解析器的单测（纯函数、最易测、也最错不起）；
补 LICENSE；发第一个 release。

### P2 · 打磨

8. Web 版能力天花板要在产品内说清楚（Firefox / Safari 无目录浏览、无 dbMode 会撞内存墙）——
   硬限制提示，别让用户卡死后再骂。
9. `message` scope 两端语义仍分歧（review §1.2 待处理）。

## 4. 后续可拓展方向（按离现有资产的距离排序）

### 近期（0–1 月）：把已有资产接成闭环

- 规则导入 / 导出 `.cep.json`（CLI 已有 schema，GUI 只差 UI）→ 团队共享、进 CI
- 引擎补齐 thread / 循环计数 / 条件表达式（消 W01 / W04 / W05）→ CEP 可无人值守
- 分析结论导出（选中链 → Markdown / JSON）→ 补上最后一公里
- CI + 前端单测 + LICENSE + 首个 release → 可对外分发

### 中期（1–3 月）：从「查看器」到「工作台」

- **规则库 / 模式市场**：模板 + 社区规则包（`.cep.json` 是天然的分发格式）
- **统计与聚合视图**：当前只有「点」没有「面」——错误率随时间曲线、级别分布、TOP N。
  这是从「看一条」到「看全局」的跃迁，也是 Kibana / Grafana 用户最熟悉的入口
- **日志聚类 / 指纹**：把海量相似错误聚成几条（Drain / Spell 类算法），直接对接 lane。
  与过滤器正交，价值极大
- **多会话对比**：「故障时段 vs 正常时段」双缓冲对照——排障最常见的动作就是找差异

### 远期（3 月+）：平台化

- **无头值守模式**：`loggraph cep` 进 CI / 定时任务，输出告警与退出码
  （退出码体系已就绪：0 / 1 / 2 / 3）→ 把工具变成服务
- **远程 / 流式日志源**：从「事后分析文件」到「实时接入」（tail -f / SSH / 对象存储）。
  这是从「离线分析器」到「可观测性前端」的跳板，也是商业化最自然的方向
- **结构化日志一等公民**：JSON 日志自动展平字段，过滤器直接写
  `level=="E" && latency>500`——条件表达式从「字符串切分」升级为「真字段查询」
- **协作与分享**：分析快照链接、标注与评论 → 把个人洞察变成团队知识库
- **AI 辅助**：自动建议过滤器 / 候选规则 / 异常摘要。
  ⚠️ 注意：这是锦上添花。在「规则、导出、统计」没做之前加 AI，
  是在没有地基的楼上加装电梯。

| 命中 | 339,010（Filter 1 = 268,569 / Filter 2 = 70,441） | 大结果集下 UI 不卡 |

### 实测新发现（静态读代码看不出来）

**① 概览缩放下时间线是两条实心色块 —— 核心价值失效（P0 级体验）**
全量视图（窗宽 206.8h）下，26.8 万 / 7 万命中被压成两条 100% 饱和的实心条，
**看不出任何结构，更谈不上"垂直对齐看关联"**。必须缩放才能看到事件。
这把「只有点、没有面」的问题从抽象判断变成了可截图的事实：
**真实数据集的默认视图，恰恰是信息量最低的视图。**
→ 缺密度直方图 / 热力聚合 / 自动缩放到有意义区间。

**② 异常数字自相矛盾（P1 准确性）**
- CEP 面板：`Group 3 · 1615 链 · 335,780 异常`
- 画布头部：`⛓ 1615 链 · 2000 异常`
2000 是 `CEP_MAX_CHAINS` 的链上限，疑似串到了异常数标签上。
两个入口对同一分组给出不同异常数，用户无从判断哪个可信。

**③ 异常语义在大结果集下不可用（P1 语义）**
2 节点规则匹配出 1615 条链，却有 335,780 个"未被覆盖的异常事件"——
绝大多数命中都成了异常。"异常"本该是稀有信号，现在是被淹没的噪声。
→ 异常需要阈值 / 聚合 / 分级，而不是逐事件罗列。

**④ 深色主题下 ReactFlow MiniMap 渲染为整块白框（P2 观感）**
画布右下角 MiniMap 是一整块白色矩形、左下角 Controls 也是未着色的白色圆形，
在深色画布上非常突兀、像是坏了。这是最高价值功能页的门面问题。

**⑤ 发布链路脆弱（P1 工程）**
- WebView2 **在启用 GPU 时启动即崩溃**（`EBWebView/Crashpad/reports/*.dmp` 可复现），
  必须 `--disable-gpu` 才能起来。若用户机器同类环境，表现为"双击后白屏/闪退"。
  建议：给 WebView2 加显式降级参数或崩溃兜底提示。
- `npm run tauri:build` **偶发** `tauri-plugin-opener` 编译崩溃
  （`STATUS_ACCESS_VIOLATION`），重跑一次成功 —— 构建不确定性，正是需要 CI 的理由。

### 静态评审结论的修正

- 「工程与性能 9 分」**维持**：1.70s 实测坐实。
- 「核心能力完成度 7 分」**下调至 6.5**：概览视图信息量过低 + 异常语义不可用，
  是比原先估计更严重的可用性缺口。
- 「交付与可持续 4 分」**维持**，且新增证据（构建偶发崩溃 + WebView2 启动崩溃）。
- 综合：**6.5 → 6.3**。P0 清单追加第 4 项「概览聚合视图」。
