## 2. 本轮兑现了什么（逐项附代码证据）

### ✅ P0① CEP 引擎能力下沉 —— 二轮称"最大一跳"，已兑现（`dd5bace`）

二轮时引擎遇到 thread / 循环计数 / 条件表达式就 fallback，规则导出到 CLI 形同虚设。本轮：

| 能力 | 落地位置 | 证据 |
|---|---|---|
| `scope:thread` 分桶 | `engine/src/cep.rs::bucket_store` / `match_bucket` | 引擎 103 测试含 3 例 thread 分桶 |
| `periodic` 心跳断言 | `assert_heartbeat`（正常段/缺口/抖动三态） | CLI 冒烟：心跳缺口计入 `lateCount` |
| `nodeCounts` 循环计数 | `match_bucket` 内连续计数（EPL `A{min,max}`） | 不足 min 即断链 |
| `nodeConditions` 条件表达式 | 新增 `engine/src/expr.rs`（401 行，端口自前端 `expr.ts`） | 未知字段编译期返回 None（= 不过滤） |

- `GroupSpec::is_supported()` 恒 `true`；`rules.rs` 移除 W01/W03/W04/W05 及 `warn` 助手；
  前端 `rulesIo.ts` 导入/导出同步去掉误告警。
- **端到端冒烟**（`cargo run -p loggraph-cli -- cep`）：引擎 JSON 落地 camelCase
  `threadStats`，证明 Tauri IPC 与 CLI 共用形状成立。
- 地基补丁：`SeqEvent` 补 `level`/`source_file`，`pipeline.rs` 改用 `parse_rest` 填充
  ——此前 message 恒空、thread/level 全 None，表达式根本无从求值。

### ✅ 规则资产可进 CI —— 二轮"只兑现四成"→ 现在成立

CLI 是真接口：`loggraph validate` 校验 → `loggraph cep --json` 跑分析 → agent 可直接判读
`.response.results.<groupId>.chains`。契约 §7 已写明 agent 使用路径。

### ✅ thread 启发式的脆弱性被诚实暴露（`2efa401`）

实测 9 种常见日志格式**只有 1 种**能解析出 thread（log4j2 线程在前的写法）；
Spring Boot / Logback 两种主流 Java 写法、nginx / syslog / Python logging 全部为 None。

处置是**可观测而非自适应**：`SeqResult.threadStats`（totalEvents/withThread/distinctThreads）
不论 scope 都回传；覆盖率为 0 时 UI 直说"此时等同全局，链会跨线程串出伪链"。
**明确禁止**靠"放宽锚定、到处找方括号"提高覆盖率——那会把漏解析（退化成全局，保守可用）
换成更坏的误抓（流被拆碎 ⇒ 零链 = 全部漏报）。理由写进契约 §3.13，防止后人反向优化。

### ✅ 版本号进位 0.1.0 → 0.2.1

### ⚠️ CEP 模板库（P1⑥）—— 二轮记为"未动"，实为误判，本轮核实已可用

`src/sequence/templates.ts`（231 行）5 条模板：超时未响应 / 失败→重试 / 心跳丢失 /
启动后崩溃 / 死锁征兆。已接入命令面板 ⌘K → 「规则模板」组
（`CommandPalette.tsx:331`），一键生成过滤器 + 分组 + 连线。

### ⚠️ 对外 release —— 半兑现：**产物已构建，但对外不可见**

- `release.yml` 三平台（Windows NSIS / macOS dmg / Linux AppImage+deb）构建**全部成功**：
  run `39018254602`，4 个 job 全绿，9m44s。
- 但 `releaseDraft: true` → release 以**草稿**创建，GitHub 公开 Release 页面显示
  "There aren't any releases here"。**用户下载不到任何一个安装包。**
- 二轮说"分发只差临门一脚"——现在这一脚就是**把草稿点成已发布**。

### 工程维度为何是唯一下调项（9.5 → 9.3）

不是退步，是**记账**：
- 增量正面：前端测试 45 → 54，引擎 100 → 103，契约同步 5 处。
- 新增债务：二轮时引擎 CEP 残缺，语义变更只需改前端；**现在两边都是全功能实现**，
  任何语义调整都要同步改两处 + 两端补测试。这是能力下沉的必然代价，必须显性记账，
  否则会误以为"下沉完成 = 债务减少"。
- 卫生死角：仓库根 0 字节 `nul`（Windows 保留设备名，安全删除机制处理不了）长期滞留。

## 5. 方法论反思：评审必须验证代码，不能只读文档

二轮把 **P1⑥ 模板库**记为"❌ 未动"，但核实提交时间戳后发现：

```
1f7f008  14:08:38  发首个 release + 二轮复评文档
70b3f07  14:08:46  CEP 规则模板库与引导式创建（P1⑥）
51152a2  14:08:54  CEP 引擎下沉 opt 边能力
```

**复评文档与模板库代码是同一批次提交的**——评审写下"未动"时，代码就在库里。

教训：评审若以文档/commit 标题为依据，会把已兑现的记为未兑现（低估），也可能把
"写了但没接线"的记为已完成（高估）。本轮对每一项都追到代码证据：
- 模板库 → 查 `CommandPalette.tsx` 是否真有入口（有，`RULE_TEMPLATES.forEach`）
- release → 查公开页面与 `releaseDraft` 配置（发现是草稿，而非"已发布"）
- 更新通道 → 查 `tauri.conf.json` 有无 updater（无）

**"提交过"≠"已交付"，"跑通 CI"≠"用户拿得到"。** 这三处差别正是本轮分数的关键。

二轮说"把 CEP 从能配变成能跑、能带走，这是 7.8 → 9 的最大一跳"——**这一跳跳过去了**。

前者点一下就行，后者是真正的工程取舍。这两件做完，它会从"我私藏的排障利器"
变成"团队愿意装、愿意写规则、愿意进 CI 的基础设施"——那时的 9 分才是
**被真实工作流验证过的 9**。
